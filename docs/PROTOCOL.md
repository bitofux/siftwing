# V2 帧头与字节序合同

本文是 V2 协议版本 1 的线格式合同，供客户端、服务端及内存 codec 使用。当前仓库有
本规范、黄金字节例子、[有界连续 Buffer](BUFFER.md)及[增量帧解码](FRAME_DECODER.md)；
编码、socket、Reactor 与网络应用尚未实现。JSON 业务
字段由对应后续模块定义，本文不将 V1 CLI 输出直接指定为网络响应。

## 传输与帧边界

传输使用 TCP。一个应用层帧由固定 24 字节帧头和紧随其后的 Body 组成。TCP 保持字节
顺序，不保持应用层帧边界；一次发送、接收或 TCP segment 不等于一帧。调用方必须允许
帧头和 Body 分片，也必须保留一次接收中多帧及末尾半帧的未消费字节。

所有多字节整数都是无符号、网络字节序（高位字节先传输）。偏移和长度以八位字节计量。
线格式不依赖 `sizeof`、对象对齐、主机端序、`packed` 结构或指针强转；64 位 request_id
也遵守相同规则，不能仅处理 16/32 位字段而漏掉它。

## 固定帧头

| Offset | Size | 字段 | 协议版本 1 的合同 |
|---:|---:|---|---|
| 0 | 4 | magic | 固定字节 `53 46 54 57`，ASCII `SFTW`；整数解释为 `0x53465457` |
| 4 | 1 | version | 固定 `1` |
| 5 | 1 | header_size | 固定 `24`（`0x18`），本版本不允许扩展头 |
| 6 | 2 | message_type | 下表中的唯一编号；请求与响应分别编号 |
| 8 | 2 | flags | 固定 `0`，任何非零位都拒绝；不默默忽略未知行为 |
| 10 | 2 | status | 请求与成功响应固定 `0`；错误响应使用已定义非零状态 |
| 12 | 4 | body_length | Body 的实际字节数，范围 `[2,1048576]`；不计帧头 |
| 16 | 8 | request_id | 范围 `[1,18446744073709551615]`；由请求方选择，响应原值回传 |

字段区间依次相邻且正好覆盖 `[0,24)`。magic 用于识别协议，不提供认证或加密。
版本不同、头长不同或者未知编号都不得按版本 1 猜测解释；格式演进需另行明确版本迁移。

## 消息编号与方向

| message_type | 编号 | 方向 | status |
|---|---|---|---|
| PING | `0x0001` | 客户端 → 服务端 | `0` |
| SERVER_INFO_REQUEST | `0x0002` | 客户端 → 服务端 | `0` |
| SEARCH_REQUEST | `0x0003` | 客户端 → 服务端 | `0` |
| SUGGEST_REQUEST | `0x0004` | 客户端 → 服务端 | `0` |
| PONG | `0x8001` | 服务端 → 客户端 | `0` |
| SERVER_INFO_RESPONSE | `0x8002` | 服务端 → 客户端 | `0` |
| SEARCH_RESPONSE | `0x8003` | 服务端 → 客户端 | `0` |
| SUGGEST_RESPONSE | `0x8004` | 服务端 → 客户端 | `0` |
| ERROR_RESPONSE | `0xffff` | 服务端 → 客户端 | 已定义的非零状态 |

高位用于编号分区，不代表可以按位推导、接纳未知类型。请求正常完成时返回对应响应；
业务失败使用 ERROR_RESPONSE，并保留原 request_id。SEARCH 无命中、SUGGEST 无候选
属于成功，不改为错误响应。接收方按自己的角色检查方向。

V2.0 每连接最多一个在途业务请求。request_id 是该连接内的请求关联号，不是 fd、
ConnectionId、generation、全局唯一身份或幂等承诺。客户端不能在前一个请求完成前
复用其编号；完成后可复用。服务端异步任务还须用 ConnectionId/generation 校验连接
生命，request_id 本身不能防止 fd 复用串响应。流水线与乱序完成不属于 V2.0。

## 错误状态

| status | 编号 | ERROR_RESPONSE 的语义 |
|---|---|---|
| OK | `0` | 仅请求和正常响应使用；ERROR_RESPONSE 不得使用 |
| INVALID_REQUEST | `1` | 已识别请求的 JSON 或业务参数非法 |
| OVERLOADED | `2` | 有界容量拒绝，任务未被接受 |
| STOPPING | `3` | 服务正在停止接收新任务 |
| INTERNAL_ERROR | `4` | 已接受请求的内部处理失败 |
| DEADLINE_EXCEEDED | `5` | 请求处理超过约定截止时间 |
| RESOURCE_LIMIT | `6` | 业务计算或结果生成超过有限预算 |

状态表达本次处理结果，不自动保证重试安全、取消已运行任务或交付成功。ERROR_RESPONSE
只允许状态 `1`—`6`；未知状态拒绝。错误 Body 仍为 JSON 对象，诊断字段留给后续业务
合同；客户端用 status 判断类别，不解析日志文字来识别错误。

## Body、容量与完整性

所有消息的 Body 都是一个 UTF-8 JSON 对象，不是字符串、数组或多个拼接 JSON 值。
帧头的长度计序列化后实际字节，不计字符数、转义前长度或 C 字符串终止符。不得额外
附加 NUL；JSON 内表示 NUL 必须使用合法转义。允许 JSON 语法规定的首尾空白，但仍
计入长度预算。PING/PONG 的 Body 固定为两个字节 `7b 7d`，即 `{}`。

版本 1 的硬上限为 1 MiB（1048576 字节）；实现可配置更小的接收上限，配置范围
`[2,1048576]`，默认 1048576。响应同样受上限约束，不把超限 JSON 截断成成功响应。
实际 JSON 和业务字段验证由后续模块完成；仅头部长度合法不证明 Body 合法。

帧总长度为 `24 + body_length`，合法范围 `[26,1048600]`。实现先验证长度与本地预算，
再以足够宽的整数计算总长，最后检查目标容器/计数类型能表示；不得在窄整数中先相加，
不得根据未经验证的长度分配 Body。`body_length=0xffffffff` 必须拒绝，不等待或分配
约 4 GiB。声明长度与实际尚未接收的字节数不同，可能只是半帧；EOF 后残留半帧才是
截断，不得发布部分请求。

## 检查顺序与失败边界

接收处理按以下合同顺序进行；内存解码已实现第 1—2 步和第 3 步的完整性等待，
Body 验证与业务响应待后续实现，没有已实现的网络行为：

1. 不足 24 字节：需要更多数据，不猜字段、不消费半个头、不交付请求。
2. 满 24 字节：检查 magic → version → header_size → message_type → flags →
   status 与类型组合 → body_length 和本地容量 → request_id → 接收角色的方向。
3. 头部合法但 Body 不完整：等待更多数据；完整后验证 UTF-8、JSON 对象及业务字段。
4. 正常请求产生对应响应；已识别请求的 Body/业务错误使用相同 request_id 的错误响应。

头部非法、超出接收上限、方向非法或 EOF 截断时终止该连接，不扫描 magic 尝试重新
同步，也不生成猜测 request_id 的错误响应。完整头部合法但请求 Body/参数非法时，若
连接及输出容量仍可用，返回 INVALID_REQUEST。接收非法响应时客户端终止该连接。
错误响应自身仍受输出容量、断连和停止策略约束，协议不保证它最终到达对端。

## 独立黄金字节

以下每组先列完整 24 字节头，后列 Body。期望字节由字段偏移手工构造，供后续 codec
测试采用；当前只核对线格式，不证明 socket、半包状态机或业务响应已实现。

### PING 请求

request_id 为 `0x0102030405060708`，Body 为 `{}`，status/flags 为 0：

```text
53 46 54 57 01 18 00 01 00 00 00 00 00 00 00 02
01 02 03 04 05 06 07 08
7b 7d
```

### 对应 PONG

关联号和 Body 保持，类型变为 `0x8001`：

```text
53 46 54 57 01 18 80 01 00 00 00 00 00 00 00 02
01 02 03 04 05 06 07 08
7b 7d
```

### 长度及关联号上界

SEARCH_REQUEST 头部，body_length 为 `0x00100000`（1048576），request_id 为全 1。
此例只有头，未附 1 MiB Body，不能当作完整帧或有效业务请求：

```text
53 46 54 57 01 18 00 03 00 00 00 00 00 10 00 00
ff ff ff ff ff ff ff ff
```

### 必须拒绝的长度

SEARCH_REQUEST 头部，body_length 为 `0xffffffff`，request_id 为 1：

```text
53 46 54 57 01 18 00 03 00 00 00 00 ff ff ff ff
00 00 00 00 00 00 00 01
```
